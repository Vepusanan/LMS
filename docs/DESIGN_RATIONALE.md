# Fōcus — design rationale

**A quieter interface with a clearer next step.** This frontend study redesigns the Faculty of Computing LMS using the supplied screenshots and the attached educational-dashboard reference. Charcoal navigation, lavender selection, generous spacing and restrained course illustrations follow the new reference; muted green and peach retain useful positive/urgent cues. The name “Fōcus” is a prototype identity, not an institutional rebrand.

| Screen / area            | Before                                                               | After and rationale                                                                                                                            |
| ------------------------ | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Home / dashboard         | Oversized image, scattered notices, contradictory timeline/calendar. | A compact learning banner, shared deadline data, an actionable next step, current classes and a small calendar reduce searching.               |
| Login                    | Weak primary action, competing guest/cookie controls, pre-filled ID. | Empty credentials, one clear login action, quiet guest entry and explicit error text clarify intent.                                           |
| Courses                  | Mixed semesters, truncated titles and arbitrary decoration.          | Semester groups, search, filters, sort, star and full titles support recognition; subject-based illustrations orient without replacing labels. |
| Course detail            | Generic topics, unexplained files, adjacent answers.                 | Named weeks, metadata, completion feedback/undo and a submitted-quiz condition make the learning sequence explicit.                            |
| Assignments              | Deadlines dispersed across views.                                    | One seeded source, statuses, complete dates, validated uploads and replace/remove controls give students a reliable action path.               |
| Timetable                | Large empty calendar dominates.                                      | Week/day views prioritise scheduled classes; ICS export supports students’ existing tools.                                                     |
| Exam registration        | Critical date buried in a notice.                                    | Closed status is explicit; a clearly separated practice form supports HCI evaluation without inventing a live registration window.             |
| Messages / notifications | Ambiguous badges and scattered updates.                              | Unread counts, priority grouping, direct action links and reversible message actions reduce uncertainty.                                       |
| Grades                   | Dashes without context.                                              | Weight/score/feedback breakdown and “Not graded yet” explain missing information; illustrative GPA is labelled.                                |
| Participants             | Uppercase names and irrelevant last-access history.                  | Search, roles, pagination and privacy-limited previews expose only useful course information.                                                  |
| Settings / help          | Inconsistent access and weak recovery.                               | Live persistent accessibility settings, predictable FAQs, support draft and a human handoff preserve control.                                  |
| Mobile / global          | Desktop-first navigation and small targets.                          | Bottom tabs, responsive day views, grade cards, focus management and command search adapt to device and input method.                          |

The assistant uses rules over local data; unknown questions receive a fallback instead of fabricated answers. Voice is optional, feature-detected and accompanied by privacy/limitations text. All uploads, messages, reset requests and registrations are visibly simulated; no backend action occurs. Settings and progress persist only in the current browser.

**Evidence boundary:** build, functional and automated accessibility checks validate implementation. They do not prove improved human usability. `HCI_ACTIVITY.md` provides the real evaluation protocol and blank observations; `/#/usability` collects task times and outcomes. Key follow-up checks are screen-reader use, real phone ergonomics, voice support, and whether students correctly distinguish a practice registration from an official application.
